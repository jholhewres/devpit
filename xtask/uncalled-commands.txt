# Commands the window never calls, and why they stay. One `name reason` per
# line; everything else in the contract has to be called from web/src.
#
# All four are the same shape: a command that exists so the generated contract
# carries a type the window does read. specta writes down what a command can
# reach, and an event payload is reachable from no command.

chat_frames carries Ask and Frame, which chat.send streams over a Channel specta cannot describe
permission_questions carries Question, which arrives on an event
terminal_happenings carries Happening, the payload of terminal:happening
terminal_block_changes carries BlockChanged, the payload of terminal:block
card_happenings carries CardHappening, the payload of card:happening
browser_showings carries Showing, the payload of browser:showing

browser_drivings carries Drove, the payload of browser:driven

# `browser_act` is the one command here a *person* never calls: it is what an
# agent would use to drive a page. And that is the honest state of US-028 in
# plan 24 — the mechanism exists, is escaped, is gated behind a grant the
# person makes, and has eight tests; what does not exist is the bridge from an
# agent to it. devpit's agents are CLIs, so reaching this means an MCP server
# or the hook endpoint, and neither is built. The command stays because the
# grant, the escaping and the page-read are the hard half; this line comes out
# when the bridge arrives.
browser_act an agent drives a page with it; the agent-side bridge is not built yet
browser_read an agent reads a page with it; same bridge, same absence

# Not for the window: the e2e calls it through `__TAURI_INTERNALS__` to ask
# where a page actually ended up, because the driver cannot see into a native
# child webview and a screenshot raised the question that reading the code
# could not settle. `add_child` takes logical pixels and `position()` reports
# physical ones; this is what makes the two comparable.
browser_where the e2e asks the window where a page really is; the driver cannot see one

# The menu is a window of its own, so its two payloads cross a boundary specta
# cannot see from a command: `MenuFor` goes out on `browser:menu-for` and `Did`
# comes back as an argument the window has to be able to name.
browser_menus carries MenuFor and Did, the payloads the menu window is told and answers with
